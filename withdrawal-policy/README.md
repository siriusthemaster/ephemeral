# Withdrawal policy (H1 to H5)

The checks the ephemeral client runs before every withdrawal from a stealth address. Pure TypeScript, no network, about 110 lines: `guards.ts`.

First, a destination nothing comes back from is blocked before any other check: the zero address, `0x000000000000000000000000000000000000dEaD`, the precompiles `0x…01` to `0x…11` (bug bounty, 31 Oct), the ERC-5564 Announcer (`0x55649E01B5Df198D18D95b5cc5051630cfD45564`) and the ERC-6538 Registry (`0x6538E6bf4B0eBd30A8Ea093027Ac2422ce5d6538`), in any letter case, and for a token withdrawal (`isToken`) the token contract itself (`tokenAddress`). The result is that one block, with no H1 to H5 lines. `destinations.test.ts` covers them.

H1 and H2 fail closed. `walletAddress` (the key wallet) and `payer` are required inputs: pass `undefined` while one is not known yet. While the key wallet or the payer is unknown (`undefined`, empty or not an address), that check blocks every destination ("cannot check, key wallet unknown" / "cannot check, payer unknown"), so Withdraw stays locked until it is known. A known payer as the destination blocks, like H1 (bug bounty, 26 Oct: the docs said "the payer is never a destination" while the check only warned); every payer counts, `payer` and each of `payers`.

Payers and the asset come from the chain, not from the announcement (bug bounty, 26 Oct). An ERC-5564 announcement is a claim anyone can make: its caller may be a relayer or a stranger, its metadata is often shorter than 57 bytes (no asset, no amount; most mainnet announcements), and a later announcement for the same address can claim any asset and amount. `funding.ts` reads what reached each stealth address and who sent it: plain ETH payments next to the announcement, ETH an explorer lists (internal transfers too, each confirmed on the node), EIP-7708 ETH logs, and Transfer logs to the address (one `eth_getLogs` pass for all addresses). `payers` holds every funding sender, every Transfer log sender and the sender of the transaction that carried it, and the caller and sender of every announcement; `payersKnown` is true only when nothing is missing (ETH found must equal the balance while the address has signed nothing; after that only an explorer can confirm it). Pass `payer` = one of them and `payers` = all of them while `payersKnown` is true, else `payer: undefined`, and H2 blocks. `paymentView` picks the announcement the chain confirms (else the earliest), gives the amount sent from the chain, flags more than one announcement for one address, and sets `assetUnknown` when what arrived cannot be read; pass it to `withdrawChecks`, and H5 treats such a payment as a token payment (block without ETH for gas, warn with it). `h2-payer-from-chain.test.ts` covers the relayed payer, token payers, every fail closed case, short metadata and a later announcement claiming 5 ETH on a 0.5 ETH payment. A node that refuses the log query for a list of addresses (some public endpoints do) is asked again one address at a time; an address whose logs still cannot be read gets the gap `logs` (set an RPC that answers `eth_getLogs` without an address), and H2 blocks. Never send these reads to a wallet's own provider as a fallback: they carry the user's stealth addresses (`rpc-split.test.ts`). ERC-1155 too (bug bounty, 31 Oct): the pass also reads `TransferSingle` and `TransferBatch` logs with `to` (topic 3) = the address, and the operator (topic 1), the sender (topic 2) and the sender of the transaction are payers; such a payment counts as a token the wallet cannot withdraw (`assetUnknown: 'nft'`). `h2-erc1155-payers.test.ts` covers both events.

`destinationsFromHistory(own, history)` turns the transfers your stealth addresses sent (read from a block explorer; the client uses Blockscout's public API) into the past destinations H3 checks against.
`historyComplete` is a required input (pass `true` only when that history fully loaded); if a caller leaves it out anyway, it counts as incomplete and H3 warns (fail safe, from the Claus Lab review).

The client never offers the key wallet as a destination and has no sweep-all button.

Study and numbers: the leak study in this repo. MIT.

`history.ts` loads those past sends from Blockscout's public API. It compares each address's on-chain nonce with the transactions the explorer has indexed: if the explorer is behind (a withdrawal made minutes ago is not indexed yet), history counts as incomplete and H3 says so. Found on mainnet on 8 Oct: a second payment was withdrawn to the same fresh address a few minutes after the first, and H3 did not warn. Likely cause: the explorer had not indexed the first withdrawal yet. Fixes: the nonce check above (`history.test.ts` covers it), and the client now records a destination as soon as a token leaves, even if the leftover-ETH step fails.

The nonces (`sentCount`) are required, not optional: every address read needs a usable on-chain nonce, keys in any case (lowercase or checksummed). A missing entry, a failed read (for example -1) or any value that is not a non-negative integer means the explorer cannot be checked against the chain, so history counts as incomplete and H3 never says "unused" (22 Oct: before, a missing entry skipped the check; `h3-sentcount.test.ts` covers it).

Token transfers are checked against the node too (Claus Lab review, 9 Oct: "the tx count can match while the reused destination is still missing from history"). `history.ts` reads every ERC-20 `Transfer` log with `from` = the address straight from the node (`eth_getLogs`, topic 1 = the address, from its first payment block to the latest block, in ranges of 10,000 blocks, smaller if the node refuses), and looks each one up among the token transfers the explorer has indexed (same transaction hash and log index). One that the explorer does not show yet makes the history incomplete, and H3 says so. The nonce cannot catch this: a transaction can be indexed before its token transfer, and a transfer relayed for the address (permit, `transferWithAuthorization`) does not use its nonce. Without a node to compare against, or when it cannot be read, history also counts as incomplete. `history.test.ts` covers both cases: the transaction count matches but one relayed token transfer is not indexed yet (incomplete), and both are indexed (complete).

ERC-1155 moves are checked the same way (bug bounty, 25 Oct): `TransferSingle` and `TransferBatch` logs carry `from` in topic 2, not topic 1, so `history.ts` also reads those two events with topic 2 = the address. An approved operator can move a stealth address's ERC-1155 token without using its nonce; if the explorer has not indexed that move yet, the history is incomplete and H3 says so.

H5 checks where the gas came from (bug bounty, 31 Oct). For a token payment (or one whose asset is unknown) it is not enough that the address holds ETH: `gasSenders(funding)` lists who sent that ETH (every ETH sender and the sender of its transaction, except ETH that came in the same transaction as the token, such as a gas tip sent with the tokens), and `withdrawChecks` takes it as `gasFrom`. Gas from the key wallet, another of your stealth addresses or a destination your payments went to blocks; gas from the payer of another payment of yours (`otherPayers`) warns, unless that address also paid this one; `gasFrom` missing or null warns. `h5-gas-source.test.ts` covers them.

ETH sends are read from their calldata too (bug bounty, 27 Oct). A transaction the address signed that moved ETH counts as a plain send to `to` only when it carries no calldata. With calldata it is a contract call (a swap router, a bridge, a multicall): `to` still counts as a past destination, but where the ETH ended up cannot be read from it, so the history is incomplete; the same for an ETH send that creates a contract (no `to`), which used to be dropped without a trace. When the explorer list lacks the calldata it is read from `/transactions/<hash>`, and input that cannot be read counts as incomplete. `h3-value-calls.test.ts` covers the router send, the creation, the zero-value control and the plain send to an EOA.

Zero-value transactions are no longer skipped (bug bounty, 25 Oct). Each one the address signed is read from its calldata: no calldata means a plain transaction, and its `to` counts as a past destination (a zero-value send to an address is still a public link); `transfer` or `transferFrom` of the address's own tokens adds the recipient, even when the token logs nothing; anything else (an approval, an unknown call, input that cannot be read) makes the history incomplete, because such a call can let tokens leave later without a trace the loader reads. `h3-zero-value-erc1155.test.ts` covers all of these.

Bug bounty, 3 to 7 Nov (`bounty-0711b.test.ts`). An ETH send with no calldata to an address with code (a forwarder, a splitter, a delegated EOA) no longer counts as a plain transfer: where the ETH went cannot be read from the send, so the history is incomplete; a payment address with code is never complete either (`NodeReader.getCode`, as in the client since 0.2.11). The P256VERIFY precompile `0x…0100` and the system address `0x…fffe` are unspendable. A token withdrawal without `tokenAddress` blocks (cannot check). `registrants` (wallets that published the meta-address) block like the key wallet (H1). Gas sent by the destination itself blocks H5. A Transfer of zero and an ERC-1155 move of zero make no payer and no arrival. On OP-stack chains a deposit a contract starts on L1 arrives from an aliased address; H2 and H5 compare the de-aliased address too (`l1Of`).
